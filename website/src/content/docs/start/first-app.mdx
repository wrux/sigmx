## Declare state, read it, change it

<Live html={`
<div data-signals="{ clicks: 0, name: '' }">
  <button data-on:click="$clicks++">Click me</button>
  <p>You clicked <b data-text="$clicks"></b> times.</p>
  <input data-bind:name placeholder="Your name">
  <p data-show="$name">Hello, <span data-text="$name"></span>!</p>
</div>
`} />

- `data-signals` creates signals from a JavaScript object literal. Signals are the only client state.
- `data-on:click` runs an expression when the event fires. `$clicks++` reads and writes the signal.
- `data-text` keeps the element's text equal to the expression. It re-runs only when a signal it read changes.
- `data-bind` is two-way: typing writes the signal, and setting the signal updates the input.
- `data-show` toggles `display: none`.

Expressions are plain JavaScript. `$name` resolves to the `name` signal; everything else (`el`, `evt`, globals) resolves as usual. See [Expressions](/guides/expressions/).

## Talk to the server

Add `@get` and an endpoint. The endpoint reads the signals the browser sent, renders HTML, and returns it. Because the returned element has the same `id` as the one on the page, sigmx morphs it in place: the input keeps focus, and only the list changes.

<Demo app source={searchSrc}><Search /></Demo>

Any server language can answer. The response the demo receives is a short text event stream: one event carrying the re-rendered list, one carrying a signal.

```
event: sigmx-patch-elements
data: elements <ul id="towns"><li>Bristol</li><li>Brighton</li></ul>

event: sigmx-patch-signals
data: signals {"results": 2}

```

A plain `text/html` response containing the same `<ul id="towns">` would work as well; the stream is only needed to update signals in the same round trip. The signals the browser sent arrive in the `sigmx` query parameter for `@get` (and in the JSON body for `@post`), so the handler reads `q` from there. Nothing about this is tied to a runtime: the format is described in [Talking to the server](/guides/server/), and a template engine in any language can produce it.

For JavaScript runtimes, `sigmx/server` builds those responses from Fetch-API primitives. The same handler in that form:

```ts
import { patchElements, patchSignals, readSignals, sse } from 'sigmx/server'

export const GET = async (request: Request) => {
  const { q = '' } = await readSignals(request)
  const matches = towns.filter((t) => t.toLowerCase().includes(String(q).toLowerCase()))
  const list = `<ul id="towns">${matches.map((t) => `<li>${t}</li>`).join('')}</ul>`
  return sse(patchElements(list), patchSignals({ results: matches.length }))
}
```

The demo above happens to be served by an Astro route on this site; the [Astro](/sdks/astro/), [Hono](/sdks/hono/) and [Rust](/sdks/rust/) SDKs wrap the same protocol for their frameworks.

Three things happen in that one response: the `<ul id="towns">` is morphed, the `results` signal is updated, and the `data-indicator:searching` signal flips back to `false` when the request finishes. Every other page on this site is built the same way; read on for the details.
